# 初心者向け：バックアップ → 未公開確認 → 公開 → 緊急復元

**今回は実行しません。Staging保存も本番公開も別途承認が必要です。**
現在の未確認事項を残したまま公開へ進まないため、各段階の停止条件を示します。

## Gate 0：現在値を確保する（読取りの許可後）

1. 正しいブログが「キノコと田舎遊び」であることを確認。ダッシュボード → デザインを開く。
   公式のStaging機能はPro等の対象プラン限定です。対象機能が見当たらない場合は停止し、無料版の保存を未公開保存と見なしたり、プランを変更したりしません。
2. 「公開中のデザイン」と「未公開のデザイン」がある場合は、**それぞれ別フォルダー**へバックアップ。未公開側を公開中と取り違えない。
3. カスタマイズの各欄で全文選択・コピーし、UTF-8のテキストとして保存する。まだ貼付け・保存しない。

| 画面・対象 | 保存するファイル | 保存内容 |
|---|---|---|
| カスタマイズ → デザインCSS | `DesignCSS.txt` | 先頭のsystem sectionを含む全文 |
| カスタマイズ → ヘッダ → ブログタイトル下 | `Header.html` | 既存画像・MENU等を含む全文 |
| カスタマイズ → フッタ | `Footer.html` | PAGE TOP、通信、その他scriptを含む全文 |
| 固定ページ → `/new-top` の編集画面 | `NewTop.html` | HTML本文全文。編集モード/タイトル/公開状態も記録。更新しない |
| スマートフォン・テーマ・トップ表示設定 | `Settings.json` | 現在値・公開中/未公開・確認日時。認証情報は含めない |

4. スマートフォンの「レスポンシブデザイン」が有効か確認する。OFFならスマホ専用Header/Footer/記事上下も別ファイルへコピーする。**勝手にONにしない**。本候補はレスポンシブ表示での受入れが必要で、OFFなら追加調査する。
5. フッター以外の「記事上」「記事下」「高度な設定のhead」、テーマID、背景、トップ記事/一覧設定、サイドバー、読者ボタン設定など変更対象に関係する欄もスクリーンショットとテキストで記録。パスワード/秘密URL/トークンは記録・共有しない。
6. コピーをPCまたは端末の永続保存先に保管。Workの一時領域だけを唯一のバックアップにしない。生のバックアップはGitHubへコミットしない。

補助ツールを利用できるPCでは、エクスポートを `private-export` に入れて次を実行すると、別フォルダーに原本をコピーし、サイズとSHA-256を記録できます。

```powershell
python tools/hatena_release_package.py backup private-export private-backup-20261024
```

既存の出力フォルダーには上書きしません。スマホだけの場合は先にファイル保存だけ行い、ハッシュ作成と差分レビューは後続で支援できます。

**停止条件：** どのデザインが公開中か不明／全文を保存できない／既存未公開変更が不明／スマホ設定未確認。バックアップ前に古いGitHub候補で全文置換しない。

## Gate 1：現在値と候補を照合して最終一式を確定する

管理者または作業担当がバックアップ全文を読み、既存の独自変更・連携を確認します。公開DOMのCSSを管理画面の生コードだと決めつけません。

1. `PROVENANCE.md` の系譜と `design.css` を照合。system section・テーマ・背景・記事/カテゴリ・既存独自CSSの差分を確認。65,536 UTF-8 bytesを超えれば停止。
2. Footerから `photoGallery` の通信scriptを**1個だけ**特定する。PAGE TOP、MENU、解析等は残す。似たscriptが複数ある／改造部分がある場合は自動処理しない。
3. 生バックアップ全ファイルのhashと、置換する通信script全体のhashをレビュー記録へ書く。`approved_for_preparation=true` はこのレビューが済んだという意味で、公開承認ではない。
   `review.example.json` は未承認の雛形です。管理者が自分でtrueに変更して照合を省略するためのファイルではありません。確認担当がレビュー結果を記入します。
4. 同じhashに対するレビューがある場合だけ、オフラインで候補を組み立てる。

```powershell
python tools/hatena_release_package.py prepare private-backup-20261024 private-prepared-20261024 --review private-review.json
```

出力される `DesignCSS.txt` / `Header.html` / `Footer.html` は、既存HeaderとFooterの他の部分を含む**全文貼付け用**です。`NewTop.html` と設定は変更されていないことをhashで確認します。`PRIVATE-DIFF.patch` はprivateに保管します。

**このPRだけでは実管理画面のhashへのレビューはまだ作れません。** レビュー未実施ならツールは停止します。レビュー済み一式を受領するまで、管理者がコードを手作業で選んで削る必要はありません。

## Gate 2：はてなのStagingで確認する（事前承認後のみ）

公式の現行手順：**「保存する」＝未公開保存、「プレビュー」＝確認、「変更を公開する」＝本番反映**。古い資料の「変更を保存する」と混同しない。実画面がこの3ボタン構成と違う場合は操作せず画面を確認します。

1. 既存の未公開デザインもバックアップ済みか再確認。
2. レビュー済み一式のDesignCSS全文を「デザインCSS」へ、Footer全文を「フッタ」へ入れる。この段階で新しいマーカーはまだHeaderへ入れない。
3. **Staging保存の明示承認後**に「保存する」を押す。「変更を公開する」は押さない。
4. 「プレビュー」で `/new-top`、通常記事、探索日記、日常の記録、その他カテゴリを確認。旧iframe通信と通常記事の回帰を先に確認する。
5. 次にレビュー済みHeader全文（既存Header＋有効化マーカー）を「ブログタイトル下」へ入れ、承認範囲内で再び「保存する」。
6. Previewの実URL/origin・body classを確認する。正しいブログoriginでrootをプレビューできない場合は停止し、匿名/別originを許可する変更をしない。
7. `/` に新トップ、その下に従来記事、購読・検索・アーカイブが残ることを確認。`/?kinoko-native=1` で新iframeがなくなることを確認。
8. 320/360/390/430/768/900/1280/1440px、Android Chrome実機で確認。写真拡大、ページ末尾から長短ページ遷移、フィルター、検索、詳細開閉、戻る進む、回転、MENU/PAGE TOPを確認。
9. 通常記事のスター・ブックマーク・コメント表示を確認する。スター追加、コメント送信、読者登録の最終操作は行わない。
10. 異常があれば、バックアップした**未公開デザイン**を各欄へ戻し「保存する」。本番公開はしない。公開中は変更されていないことを別タブで確認。

Stagingで成功した画面と確認日時を保存し、管理者が最終承認するまでは公開へ進みません。実機未確認をデスクトップのタッチ模擬で代替した扱いにしません。

## Gate 3：本番切替（別途明示承認が必要）

1. 対象PRの最終HEAD・CI成功・保護データ・Staging受入れを再確認。日次同期による正当な増加は調査して基準を更新し、古い件数に戻さない。
2. 公開中・未公開のバックアップを再取得。Stagingと公開予定一式のhashが受入れ時と同じか照合。変わっていたら停止。
3. 設定内容と公開範囲を管理者に提示し、**はてなデザインの本番公開**の承認を得る。GitHubマージ/Pages生成は同じ承認に含めない。
4. すべての欄が検証済みStagingになっている状態で、画面右上の**「変更を公開する」**を押す。確認ダイアログがあれば対象ブログと変更内容を確認する。未確認の「公開」「更新」ボタンは押さない。
5. `/new-top` 固定ページ本文は変更・更新しない。ブログ設定のURL、記事ディレクトリ、公開範囲、RSS設定を変更しない。通常記事も公開しない。

| 欄 | 反映するもの | 方法 |
|---|---|---|
| デザインCSS | private-preparedのDesignCSS全文 | 全文置換。旧候補の後ろに追加しない |
| フッタ | private-preparedのFooter全文 | 既存他処理を保持した組立て済み全文へ置換 |
| ブログタイトル下 | private-preparedのHeader全文 | 既存Header＋マーカーの全文へ置換 |
| `/new-top` 本文・通常記事・他設定 | なし | 変更しない |

GitHub側の事前マージ・本番再生成は不要です。資料をmainへ保存するマージを後日行う場合も、mainのpushで既存生成が起動し得るため別承認にします。

## Gate 4：公開後の確認

- [ ] 正式 `/` は200、URLが変わらず、新トップと下の通常記事が表示される。
- [ ] `/new-top` も同じURLで200、本文を変更していない。
- [ ] 通常記事・両カテゴリ・/archive・検索・月別アーカイブ・読者ボタンへ到達できる。
- [ ] canonical/OGP/title/feed URLは承認前と同じ。無断のnoindexや転送なし。
- [ ] 図鑑・特徴・季節・Best Shot/年間Best・研究室のリンク、iframeの長短遷移、写真拡大が正常。
- [ ] 8幅と実Androidで見切れ・重なり・巨大空白・スクロール飛びなし。
- [ ] はてなスター件数・公式追加UI・ブックマーク・既存コメントが表示される。試し投稿/追加はしない。
- [ ] RSS/Atom取得が正常。読者通知・グループ掲載は、後日管理者が通常記事を本当に公開した際に確認する（テスト用投稿をしない）。
- [ ] 次回の定期同期と読取専用削除監査が成功。公開写真/保護参照/Best/通知/研究/退役に意図しない変化なし。
- [ ] 公開コメントconfigはenabled=falseのまま。Cloudflare変更なし。

## 緊急復元

**入口だけの退避：** `/?kinoko-native=1` ならこの起動処理は動きません。これは利用者の一時退避で、設定の復元ではありません。

**rootだけ停止：** 正常なCSS/フッターはそのままに、Headerから今回のマーカーだけを除いたレビュー済みHeader全文をStagingへ戻す。確認後、別途緊急復元の承認を得て「変更を公開する」。再読込みでrootの新iframeが作成されなくなります。

**全デザイン復元：**
1. 切替直前の**公開中**バックアップとSHA256.jsonを選ぶ。古いGitHub候補や、別の未公開バックアップを代用品にしない。
2. Header、Footer、DesignCSSを原本全文へ戻す。途中の一部だけを削って解決しない。
3. 「保存する」→「プレビュー」で旧トップ/記事/スマホを確認。
4. 緊急復元の公開承認後「変更を公開する」。`/` と記事の復旧、feed/canonical、旧iframeを確認。
5. 元々保存してあった未公開デザインが必要なら、その別バックアップを後から未公開側へ復元する。無断廃棄しない。

今回GitHub Pages側には変更がないため、Pagesの巻戻し・main reset・データ復元は不要です。日次生成による正当な更新を古いgh-pages SHAへ戻してはいけません。追加の障害があれば原因を切り分けます。
