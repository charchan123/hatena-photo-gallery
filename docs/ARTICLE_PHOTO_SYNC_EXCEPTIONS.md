# 記事・写真の同期管理：例外案件（Phase 2b）

通常の日次同期は変更しません。高信頼の新規写真は人間承認なしで自動追加されます。「確認済み」「保留」はローカル監査であり、通常同期を許可・停止する権限ではありません。

## 実際に公開候補へ適用できる機能

既存公開写真の**名前修正**を、1写真・1マニフェストの個別移行として扱います。既存ギャラリーに収録済みで、名前が「不明」以外の未分類・曖昧写真も対象になり得ます。以下をすべて満たす場合に限ります。

- 公開snapshotと今回の公開記事API GET取得が健全で、対象のAtom記事ID・元画像URLが完全一致。
- 画像URLが全公開記事DOM・ギャラリーを通じて1回だけ出現。同一URL複数枚や複数記事の対応づけは未対応。
- 元のPhase 3Cが正常。raw portalが画像をexact gallery/legacy nameで対応づけている。
- 既存写真IDが一致し、ベストショット・研究室・同定履歴に参照されていない。
- 人間が写真を確認し、既存subject taxonomyのキノコcanonical nameを入力。新しい生物学的知識は追加しない。
- 根拠メモの入力、実生成プレビュー、旧名・新名の再入力による明示承認。
- 初回適用時には承認元の公開snapshot SHA-256が完全一致。レビュー中・PRマージ後の初回適用前に公開snapshotが更新されたら承認は失効し、再レビューが必要。

## Windowsでの手順

1. 最新mainを取得し、Python依存をインストールします。GitHub CLIを認証します。
2. ローカルの既存はてな認証設定（`HATENA_USER` / `HATENA_BLOG_ID` / `HATENA_API_KEY`）をサーバーだけへ設定します。キーを画面やPRへ貼り付けません。
3. `python -m admin.server` で127.0.0.1:8765を開き、「記事・写真の同期管理」を選択します。
4. 「公開記事をGET取得」の既存ボタンで現在の状態を取得します。「既存の公開写真（名前修正）」または従来からの確認待ちを検索します。
5. 写真・記事・現在名・検出名・根拠・撮影日（ある場合）を確認し、根拠メモを入力。「名前修正を提案」で正確な名前を入力します。
6. 対応可能な候補だけに「この名前修正を実生成プレビュー」が現れます。参照保護、重複、taxonomy一致、元のPhase 3C、全生成ページを検証します。
7. 「この写真名変更を明示承認」で旧名・新名を再入力します。まだ公開されません。
8. 「承認済み名前変更のDraft PRを作成」。実行checkoutはcleanな最新mainでなければなりません。隔離worktreeで認証済みGET実生成、全pytest、全JSテスト、diff-check、公開状態の再取得を行います。
9. Draft PRの変更は `sync-migrations/photo-names/<migration SHA-256>.json` 1ファイルのみ。人間がPRをレビューしてマージするまで適用されません。管理画面はmerge/deployしません。

根拠メモ全文・画面操作の履歴はignored `admin/local-state/sync/review.json` に保存します。PRにはメモのSHA-256だけを含めます。再起動後は再プレビュー・再承認が必要です。ブラウザーは任意の保存パス・元URL・旧IDを指定できません。

## 翌日も修正を維持する方法

`sync_exceptions.py` はPhase 3Cのraw検証後、独立した安全性検証を行います。対象の元画像descriptor・元検出名・元分類情報のfingerprintを照合し、その1つのproduction entryの表示名だけを変更します。portalを再構築して図鑑・五十音・季節・特徴・詳細・観察記録・favoritesのデータを一貫させます。元のdetected label / shadow gallery name / confidenceは書き換えません。人間による修正が検出器の推定と異なる場合は既存の `manual_review_name_conflict` 状態を保持します。

写真数・画像URL・記事ID・写真IDを変更しません。一般の `reconcile_ids()` は変更せず実行し、承認対象以外の名前変更・画像置換・削除・曖昧な重複・unsafe新規写真は従来どおりBLOCKEDです。

最初の適用後、公開snapshotにはマニフェストのハッシュ・対象ID・承認名のハッシュ・初回適用日時だけの台帳を付けます。以降はその台帳とGit管理された不変のマニフェストを必ず照合し、元の対象画像の根拠が同じなら修正を再適用します。記事順・`article_N`・対象外の本文/更新日時だけの変化は本人識別には使いません。対象画像の分類根拠やURL、出現回数が変わると再確認が必要です。

適用済みマニフェストの欠落・改変、台帳の改変、別写真へのすり替えは停止します。一度適用した対象への2つ目のマニフェストは拒否します。取り消し・再修正は別の個別移行として後続で設計します。

`article_sync.run()` は一時生成がすべて成功した場合だけ出力を置換する従来方式を維持します。失敗時は旧サイトの全ファイルを保持します。`python main.py` の単独実行は従来のraw生成プレビューであり、公開snapshotの照合を伴う個別移行は実行しません。本番の日次workflowは従来どおり `article_sync.py` を使用します。

## 今回未対応の操作

| 操作 | 扱い・理由 |
|---|---|
| ギャラリー未収録の未分類画像を追加 | ローカル提案・保留のみ。元のPhase 3Cにないoccurrenceの独立した検証・各出力への対応が未証明。通常の高信頼自動追加とは別。 |
| 「不明」写真・研究室対象の再分類 | 既存の研究室同定機能を利用。研究室ケースIDや同定履歴への影響があるため、この個別移行では禁止。 |
| ベストショット等の保護参照がある写真の名前修正 | 禁止。参照先の意味の変更も避ける。 |
| 写真URL置換 | 要個別移行。画像内容の同一性証拠なしに位置・名前だけから推測しない。 |
| 写真削除・対象外化 | 要個別移行。将来の再登場防止・inventory削除との関係・各出力の完全除外をまだ独立証明していない。汎用削除allow-listは作らない。 |
| 同一URL重複の名前修正 | 要個別移行。個別出現の同一性を証明できない。 |
| 適用済み修正の取消・再修正 | 要個別移行。不変台帳を編集して戻さない。 |
