# 図鑑解説への接続（第2段階設計案）

第1段階の管理室では、確認記録をローカルで審査します。この設計の接続処理、Draft PR作成、公開の入り口はまだ実装していません。

## 接続承認の対象

観測ID単位の新しい図鑑接続台帳を設け、既存の分類台帳や同期指示から独立させます。各候補に現在の掲載名、正規種ID、掲載グループ全体の観測ID集合、写真内容のハッシュと記事ID・出現位置、写真確認の対象・改訂番号、審査済み原稿と出典のハッシュを保持します。記録には承認範囲と確認者、理由を持たせ、個人の確認メモの本文は公開用データから除外します。旧 #163 の範囲は照合した3枚に限定します。

接続命令を作る際に、最新公開データと原稿のコピーから適用対象を復元し、次の項目を個別に検証します。

| 承認 | 接続での条件 |
| --- | --- |
| 写真と名称 | 最新の掲載グループに属する全写真について、必要な人間の目視確認が揃う |
| 図鑑原稿 | 審査対象の正規種IDと原稿・出典が照合でき、全写真へ適用できることを別途判断している |
| 食毒情報 | 承認済みの出典付き項目だけを食毒欄へ使用できる。本文や注意欄に未承認情報を移すことも検出して停止する |
| 特徴検索 | 割当候補の個別承認を照合する。未承認の候補で既存の特徴索引を更新しない |
| 公開 | 他の審査とは別に、生成差分と対象HEADを確認し、人間が実施を承認する |

`project_guide_expansion` は現行の分類条件を維持します。将来の実装では、その投影ルールを緩和せず、図鑑の詳細レンダラーが読む別の接続レイヤーを導入します。観測の `classification`、掲載名・撮影日、日次同期の照合結果、削除・手動採用台帳、既存の特徴検索や研究室の索引は接続レイヤーから更新できない構造にします。複数の正規種候補がある項目や分類名そのものを変更する必要がある項目は、個別検討に戻します。

## オフラインの検証手順

1. 本番生成物と同じコミットを一時領域に展開し、正例・負例の台帳を生成します。公開データの原本は読み取り専用にします。実験用の出力先は一時ディレクトリに固定します。
2. 旧ルールで接続できない `legacy_review` の写真について、全観測の確認が有効な場合だけ、詳細画面に図鑑解説が出ることを確認します。同じテストで、観測・分類・特徴索引の構造が変更前と一致することを比較します。
3. 写真1枚の未確認、画像の差し替え、記事や原稿・出典の変更、写真の追加や欠落、分類より後の再承認、旧3枚以外の追加、JSONから復元した確認だけなどを個別に与えます。条件不足の項目に種解説が出ないこと、それ以外の既存ページが変化しないことを確認します。
4. 食毒や類似種の注意が未承認のケースは、食毒欄・特記事項・本文・検索データのすべてを検査します。特徴の未承認候補は索引に現れないことを確認します。いずれも除外しきれない原稿は候補から外します。
5. 生成物の差分を、許可した図鑑詳細ページだけに制限します。写真・記事・撮影日・掲載名・分類、図鑑の既存ページと出典、Best Shot、研究室、コメント、同期履歴・保護台帳の差分は停止条件です。通常の同期によるデータ増減は比較起点を更新して別記録に残します。
6. 将来の別承認後に、既存の孤立worktree、最新mainの再確認、対象ファイルの許可リスト、差分プレビューの仕組みを使って専用Draft PRを作ります。公開工程はさらに別の承認とし、条件が変われば候補に戻します。
