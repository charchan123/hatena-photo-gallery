## A. スマートフォン通知と公式返信

### LINEとWeb Pushの比較・推奨

| 観点 | LINE Messaging API | Web Push |
|---|---|---|
| 到達先 | 管理者の既存LINE。公式アカウントの友だち/宛先の安全な紐付けが必要 | Androidの対応ブラウザに通知権限とService Workerを登録 |
| 費用 | 日本のコミュニケーションプラン例：0円/月、200通/月まで。宛先人数でも数える | VAPID/Web PushにLINEのような通数契約はない。Worker/DB/送信処理の使用量は発生 |
| 気づきやすさ | 日常使うLINEにまとめやすい。ただしブロック・OS通知無効・配信障害で届かない | ブラウザ/OS/省電力/購読失効に左右され、Android実機で確認が必要 |
| 初期設定 | 公式アカウント・Messaging API・secret・友だち/本人確認が必要 | HTTPS管理画面、通知許可、Service Worker、VAPID、購読の更新/解除が必要 |
| 運用 | 月通数監視、集約、宛先/鍵の管理 | 古い購読の除去、鍵・端末移行、通知許可の説明 |
| 機密性 | 本文をLINEへ送ると第三者へ複製される | 暗号化配送でも通知文はロック画面等へ出る |

**初期推奨：管理者1名へのLINE通知＋Access付き独立スマホ管理画面。** スマホ中心の日常運用に合わせた判断であり、配信保証ではない。LINE連携を望まない、または将来月200通では不足する場合はWeb Pushを代替・補助として検証する。LINE Notifyは採用しない。どちらの通知も正本にせず、管理画面の未確認一覧を必ず残す。

### 通知フロー

1. 一般投稿のD1 commitと同じtransactionでoutboxを1件作る。送信失敗でコメントを失わせない。
2. 少量の定期処理が期限付きleaseで取得し、一定時間の新着を集約する。初期候補は60秒集約・1分に1通知・管理者1名・月180通上限（残り20通を試験/手動連絡の余裕とする）。全て管理者判断で確定する。
3. 固定登録した本人宛先だけへ送信し、同じoutbox IDで重複を防ぐ。LINEのretry keyを最初の要求から固定する。timeoutでは送信済みか不明なので新規キーで再送しない。429/5xxはbackoff、期限と最大試行回数を設ける。
4. LINEの200応答は端末への配達/既読の保証ではない。月通数を照会し、送信前にDBの予算を原子的に確保する。他のツールの送信分も考慮し、専用アカウントを推奨。超過は通知を止め管理画面へ表示する。有料へ自動移行しない。
5. 通知は「研究室に新着コメント3件」のような最小情報と、固定HTTPS管理originの `comments/{comment_uuid}` へのリンクだけ。本文・削除キー・認証token・メールは含めない。投稿本文からURLや宛先を作らない。

### スマホ管理画面と認証

- Windows管理室は引き続きlocalhost専用。新しい管理Webは独立Worker/専用originをAccessで保護し、コメント管理APIへサーバー側で接続する。Windowsへのトンネルは作らない。
- Accessで許可した管理者を、検証済みissuer/AUD/subとサーバーのadmin_principalsで認可する。一般ユーザーやservice tokenの認証成功だけで返信権限を与えない。Cloudflareアカウントの全メンバーやドメイン全員を安易に管理者にしない。
- セッション候補は1時間、返信など重要操作前に直近15分の再認証を要求。IdPのMFAを優先し、退任/紛失端末でセッションと権限を失効できるようにする。JWT・セッションtokenはlocalStorageに置かない。CookieはSecure/HttpOnly/SameSiteを指定し、ログアウト後に管理データを残さない。
- POSTはOrigin/CSRF/Content-Typeを確認し、公式roleをサーバーが設定する。ブラウザへ管理Bearer/Cloudflare tokenを渡さない。
- 深いリンクはケースIDとコメントIDの存在・所属を認証後に照合する。戻り先は同一originの許可パスだけ。通知URLを知っていても権限にならない。
- 返信画面は対象ケース・相手の本文・返信文・「管理人として公開」を確認し、明示送信。二重tapをロックし、固定request IDで再確認する。下書きは端末に保存するか選択でき、保存範囲/期限を明示する。失敗時は文面を保持する。
- admin_auditは操作・対象ID・時刻・最小化した管理者IDを保存。通知宛先の追加/変更は再認証と確認が必要。コメント投稿者が通知先を追加できない。

Web Push採用時は、認証後の明示操作でだけ通知権限を要求し、暗号化endpoint/keysをサーバーで最小保存する。404/410で購読を無効にし、端末ごとに解除可能とする。権限拒否を繰り返し催促しない。Service Workerは公開ブログと管理画面でoriginを分け、Accessセッション切れでも機密情報をcacheから表示しない。通知をtapすると認証済みの該当コメントへ移動する。

## B. ニックネームのなりすまし対策

### 予約語（公開前の候補）

既存の管理/公式/運営/admin等に加え、**公開・管理人・ふすべまる**を一般利用者に使用させない。「ふすべまる」は管理者専用。これは今回の仕様候補であり、現行Workerに追加済みとはしない。

名前の正規化をサーバーの共通関数に集める。原表記は表示用として保持し、比較用はNFKC、Latin case-fold、空白・ゼロ幅/制御/区切りの除去、カナ→ひらがな等を段階的に適用する。「公 開」「公・開」「フスベマル」「ﾌｽﾍﾞﾏﾙ」「ふすべまる＋記号」などを試験する。正規化versionを保存する。見た目が似た別文字・漢字/かなの言い換えを完全には判定できないため、類似名を確認対象にし、管理者は専用バッジでも識別する。公式表示の権限は名前では決めない。

過去のコメントのニックネームを無断変更しない。既存名を監査し、衝突があれば新規claimだけを止め管理者へ提示する。正規化更新で既存別人のclaimを勝手に統合しない。

### ログインなしの継続利用

- 初回に256bit以上の匿名owner keyを安全乱数で生成する。サーバーはkey ID＋HMAC/鍵付きhashだけ保存し、各コメントにnullable owner_idを追加する。現行のコメント単位delete_tokenとは分離し、過去コメントの削除権限を名前だけから復元しない。
- nickname_claimsの正規化keyをUNIQUEにし、名前取得・変更はtransactionで競合を拒否する。所有者の秘密を提示した場合だけ同じ名前を継続利用できる。別人が同じ名前で投稿することは拒否する。
- 取得/変更にもTurnstileと回数制限を適用。1 ownerの保持名数を小さくし、大量先取りを抑える。未使用の仮確保は短期で失効させるが、公開投稿に使った名前は勝手に再割当てしない。
- 名前は身元証明ではない。「ログインなし・このブラウザで同じ投稿者として継続」と説明する。共有PC、XSS、拡張機能、鍵コピーのリスクは残る。名前の表示と恒久owner IDを分け、氏名やメールの収集は基本不要とする。

| 状況 | 方針候補 |
|---|---|
| ブラウザデータ消失 | 名前だけでは所有権を戻さない。事前発行の回復用秘密か別途審査。過去コメント・名前claimは消さない |
| 別端末 | 本人の明示操作で短期・単回の移行コード/QRを発行。秘密をURL queryやチャットへ載せず、使用済みは失効。任意passkeyを将来検討 |
| 悪意ある先取り | 予約語を先に登録。取引/売買を認めない。既存実績と証拠を管理者が確認し、再割当ては履歴を残し別承認 |
| 似た文字 | 正規化と類似検出、確認待ち、バッジ・投稿者識別の補助。完全防止と断言しない |
| owner key漏えい | 回復用資格情報で失効・rotation。失効前後の履歴を保持。公式権限には昇格しない |

所有権を後付けするmigrationでは既存匿名コメントを特定ownerへ推測で割り当てない。コメント単位の既存削除キーを正しく提示しても、他コメントや同名全体の所有権は与えない。

## C. 同定までの調査過程

### 時系列のモデル

恒久case_idを軸に、初期写真/候補、最初の観察、訪問者情報、追加調査/専門家、候補変更理由、確定結果/根拠をeventとして保存する。コメントID・写真observation_id・元記事への参照は残し、名前を変えてもケースを再採番しない。

research_events案：event_id、case_id、event_type、effective_date（観察日）、recorded_at（記録時刻）、actor_type、根拠テキスト、linked_comment_id、status、supersedes_event_id、確認した管理者ID。research_sourcesとevent_evidenceで出典URL・資料名・観察条件・写真参照を紐付ける。日付不明は不明とし、記事公開日を撮影日へ流用しない。

**状態：未調査 → 調査中 → 有力候補 → 同定確定**。各段階で「推測」「有力候補」「確認済み」をテキストと色・アイコンで併記し、色だけに依存しない。専門家の意見を記録しても自動確定しない。候補名・確度・根拠・確認者の明示が必須で、訪問者の多数決やAI出力だけで確定しない。

コメントは通常のコメントとして残し、管理者が確認したものだけを調査eventへ参照する。表示/引用する範囲や投稿者名への配慮を決める。本人がコメントを削除したら、event内の本文コピーも残さず「参照元は削除済み」とする。確定根拠を削除コメントだけに依存させず、別の検証可能な根拠を要求する。元コメントを復活させない。

### 変更・同定台帳との整合

既存 `data/research-identifications.json` と研究同定/再調査/アーカイブが正本である範囲は維持する。D1のeventとGitの同定情報は一つのtransactionにできないため、D1で承認候補を作り、Gitの承認PR・最終commit SHAを照合してから「反映済み」とする二段階方式を設計する。片側失敗は確認待ちとし、反映前に確定表示しない。日次同期へD1依存を追加しない。

訂正は追記のeventで旧eventをsupersedeし、旧根拠・判断履歴を消さない。ケースの統合/分割は手動review・参照表・移行計画が必要で、コメントを別ケースへ勝手に移さない。写真保護・既存alias・アーカイブを維持する。

### 画面候補

「調査ノート」として日付、候補、証拠、次の確認ポイントをカード表示。PCは時系列と写真を並べ、スマホは1列、長い根拠は開閉。訪問者情報と管理者の確認済み調査を見分けられるようにし、個人攻撃や断定を促す評価機能は設けない。500文字コメント制限と、管理者による根拠ノートの上限は別に設計する。

## 後続PRの受入条件

- A：認証前の深いリンク拒否、CSRF/権限/MFA・失効、送信前の対象確認、二重tap/再送、本文漏えいなし、通知上限・失敗時の未確認一覧、Android実機。
- B：予約語全変形、同時claim競合、同一本人の継続、鍵紛失/rotation/別端末、既存匿名の非推測移行、正規化version更新で衝突安全停止。
- C：初期候補/有力/確定の区別、根拠なし確定の拒否、Git/D1片側失敗、再調査/訂正/アーカイブ、コメント削除時の引用消去、名前変更/統合/分割で履歴保持。
- 全て別Draft PRで実装・監査し、本番migrationと通知送信・公開にはその時点の承認が必要。
